Three approaches to the Media Gallery

The main architectural decision is how folders/tags are stored and whether we add new server routes.

ARCHITECTURE
Builder JS
media-gallery.js
→
Existing CMS
/api/cms/media/*
⚠ Auth stripped from CMS endpoints
+ 1 new route: /api/cms/media/download
Folder/tag metadata: media-meta.json on server

A — Patch the CMS endpoints

Strip auth from existing /api/cms/media/* routes (builder doesn't use CMS auth), add one new URL-download route, store folder metadata in a sidecar JSON. Minimal server work but ties builder to CMS internals.

ARCHITECTURE — RECOMMENDED
Builder JS
media-gallery.js
→
New routes
/api/media/*
GET /api/media
POST /api/media/upload
POST /api/media/download
PATCH /api/media/:id
DELETE /api/media/:id
Folder/tag metadata: media-meta.json · shared media/ folder with CMS

B — New /api/media/* routes (recommended)

Clean dedicated endpoints, no auth, include folder/tag metadata from day one. Shares the same media/ storage folder with CMS so files are compatible. More server code but no coupling to CMS internals.

ARCHITECTURE
Builder JS
media-gallery.js
→
Existing CMS upload
+ localStorage meta
Upload: POST /api/cms/media/upload (no auth change)
Folder/tag metadata: localStorage only
⚠ Metadata lost on browser clear or new device

C — Upload to CMS, metadata in localStorage

No new server routes at all — upload uses the existing CMS endpoint (already no-auth for the POST), folder/tag data lives in localStorage. Fastest to build but organisation data isn't durable.
